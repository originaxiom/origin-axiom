## Specification One — Self-Referential Benchmark and Calibration Check

### What the Check Inspects and Refuses
In any verification, renormalization-group, anomalous-dimension, spectral, or quadrature script that claims to validate a solver or integrator against a benchmark or literature trajectory, the check traces the static call graph and variable dataflow inside the module and across sibling helper modules in the same folder:
- **Refuses** any benchmark or calibration assertion where the target value, reference curve, or expected dictionary is computed by calling a solver, differential-equation integrator, beta-function routine, or stepping loop defined in (or aliased from) the same script or sibling helper module under test — including indirect calls routed through local wrapper functions, anonymous lambda expressions, dictionary dispatch tables, function-attribute aliases, or re-running the same integrator with a finer step size and calling the finer run an external benchmark.
- **Refuses** any benchmark check that writes a solver's own output to a local JSON or text file and reads that same generated file back inside the benchmark check as if it were an external reference fixture.

### What the Check Must Let Through
- **Lets through** a benchmark check whose expected value is a closed-form exact rational or algebraic formula derived independently of the numerical integrator (for example, comparing a numerical one-loop running integral against an explicit rational logarithm formula that shares zero functions with the integrator).
- **Lets through** a benchmark check that compares the integrator's output against a tracked, provenance-pinned external literature table whose entries were committed as static constants citing their published source rather than generated by the solver.
- **Lets through** pure internal self-consistency checks (such as step-halving convergence tests or forward-then-backward reversibility checks) provided they are labelled as internal convergence or reversibility checks and never labelled as benchmark or literature gates.

### Planted Fault Cases in Words
- **Planted Case One-A (Direct Self-Call Benchmark):** A script defines an anomalous-dimension integrator function, calls that same integrator function at a reference boundary condition to build a variable named reference trajectory, calls it a second time with slightly perturbed step count, and asserts that the two trajectories agree to three significant figures under a heading or dictionary key claiming benchmark verification. **Expected outcome:** `REFUSE`, naming the solver function and reporting that the benchmark target flows from the module's own integrator rather than an independent reference.
- **Planted Case One-B (Lambda and Dictionary-Dispatch Alias):** A script stores its differential-equation stepper inside a two-entry dispatch dictionary under the key `"reference"`, binds a local lambda around that dictionary lookup, and asserts that the main solver matches the lambda's output. **Expected outcome:** `REFUSE`, tracing the alias through the dictionary entry and lambda wrapper back to the module's own stepper.
- **Planted Case One-C (Write-Then-Read Self-Fixture):** A script runs its solver during a setup helper, writes the resulting numbers to a sibling file in the same verification folder, reloads that sibling file in a second function, and asserts agreement as a literature benchmark check. **Expected outcome:** `REFUSE`, reporting that the purported benchmark file is written by the producer itself within the same package.

### Clean Control Cases in Words
- **Clean Control One-A (Closed-Form Exact Analytical Reference):** A script integrates a linear differential system numerically and asserts agreement against an explicit closed-form matrix-exponential rational expression that calls none of the integrator's functions. **Expected outcome:** `PASS`.
- **Clean Control One-B (Labelled Step-Halving Convergence Control):** A script runs its integrator at step size `h` and step size `h` divided by two to verify fourth-order Richardson convergence, naming the check a step-halving convergence control and making zero claim of literature benchmark validation. **Expected outcome:** `PASS`.

## Specification Two — Nested Container and Constant-Folded Claim-Bearing Truth Flags

### What the Check Inspects and Refuses
Across frontier producer scripts and verification builders that emit structured result dictionaries, tables, or JSON summaries, the check walks the full abstract syntax tree of every return value, yielded record, and JSON-serialized structure to arbitrary nesting depth:
- **Refuses** any claim-bearing boolean or zero-residual entry — such as keys or fields asserting extension to a cover, eigenvector invariance, norm preservation, anomaly cancellation, phase vanishing, unimodularity, uniqueness, or gate passage — whose value is a literal boolean (`True`), a literal zero (`zero` or `zero point zero`), or a constant-folded expression over literals, regardless of whether it sits at top level or inside nested lists, tuples, sets, comprehensions, conditional expressions, or dictionary merges.
- **Refuses** trivial constant-folding disguises, including boolean casts of nonzero integer or non-empty string literals, comparisons between two constant literals (such as one equals one, or zero less than one part in a trillion), `all` applied to an empty list literal, or `not False`.

### What the Check Must Let Through
- **Lets through** boolean or residual fields computed from genuine non-constant matrix, polynomial, lattice, or modular-arithmetic expressions over constructed mathematical objects (for example, testing whether every entry of an explicitly multiplied commutator matrix modulo an integer `N` equals zero, or whether the exact rational determinant of a constructed Gram matrix equals one).
- **Lets through** static metadata flags that describe configuration rather than mathematical truth (such as `"uses_data": False`, `"instrument": False`, or command-line argument defaults).

### Planted Fault Cases in Words
- **Planted Case Two-A (Deeply Nested Tuple-in-List Literal Flag):** A verification script returns a summary dictionary containing a `"sectors"` list of three-element tuples, whose third element is a nested dictionary setting `"extends_to_cover"` to literal `True` and `"bar_theta_residual"` to literal floating-point zero. **Expected outcome:** `REFUSE`, naming the file, container path, and literal claim-bearing entries.
- **Planted Case Two-B (Constant-Folded Cast and Literal Comparison):** Instead of writing `True`, a script sets `"monodromy_closes"` to the boolean cast of integer literal one and sets `"norm_preserved"` to the comparison `"zero less than one tenth to the twelfth power"`. **Expected outcome:** `REFUSE`, reporting that every operand of the expression is a compile-time constant independent of any computed operator.
- **Planted Case Two-C (Default-True Dictionary Merge):** A script initializes a template dictionary with `"all_checks_pass": True`, merges computed labels over unrelated keys while never overwriting `"all_checks_pass"`, and writes the merged dictionary to JSON. **Expected outcome:** `REFUSE`, reporting that `"all_checks_pass"` reaches serialization with its literal `True` initializer untouched by any computed check.

### Clean Control Cases in Words
- **Clean Control Two-A (Exact Rational Gram Determinant Check):** A lattice script constructs twenty-four basis vectors over exact rationals, forms their inner-product matrix by explicit summation, computes the exact Gaussian-elimination determinant, and sets `"is_unimodular"` to whether that computed determinant equals exact rational one and `"is_even"` to whether every diagonal entry modulo two equals zero. **Expected outcome:** `PASS`.
- **Clean Control Two-B (Declared Non-Claim Metadata Flag):** An arc metadata builder writes `"ready_for_the_final_reading": False` and `"uses_measured_targets": False` as explicit negative governance ceilings. **Expected outcome:** `PASS`.

## Specification Three — Cross-File Helper-Module and Sidecar-Table Post-Inspection Constants

### What the Check Inspects and Refuses
To enforce the rule against post-inspection parameter or modulus selection and hidden magic numbers across multi-file verification folders:
- **Refuses** any derivation, stabilization, or parameter-free claim script that avoids inline magic constants in its main file by importing numeric coordinates, tuned weights, rational offsets, or target moduli from a sibling helper Python module, loading them from a sibling JSON, CSV, or plain-text table in the same folder, or reconstructing them through string parsing, character-code arithmetic, or attribute lookup (`getattr`) on a helper object, without pricing each imported choice in the input ledger.
- **Refuses** any potential or objective function claimed to stabilize a vacuum or modulus dynamically when the potential's formula — after resolving all cross-module constants and default keyword arguments — embeds the target coordinates as subtracted offsets (such as squaring the difference between the variable and the target point by hand).

### What the Check Must Let Through
- **Lets through** mathematical constants derived inside the helper module from first-principles integer equations (for example, solving the quadratic equation `x` squared minus `x` minus one equals zero symbolically or finding the fixed point of a word of two-by-two integer matrices without embedding the root beforehand).
- **Lets through** shared exact-arithmetic utility helpers (such as exact rational determinant, Smith normal form, or permutation-parity routines) that export algorithms rather than unpriced numeric constants.
- **Lets through** constants explicitly registered and priced as borrowed inputs in the closure map's structured input inventory.

## Specification Four — Scientific-Notation, Grouped-Digit, and String-Wrapped Unpriced Dimensionful Constants

- **Refuses** formulas that divide two unpriced dimensionful constants inline (such as dividing an inline Z-boson mass literal in GeV by an inline electroweak vacuum expectation value literal in GeV) while counting zero imported dimensionless ratios in the script's input tally.

### What the Check Must Let Through
- **Lets through** pure mathematical precision settings (such as setting working decimal precision in an arbitrary-precision library to forty or eighty digits) and numerical convergence tolerances explicitly bound to assertion thresholds (such as checking that a quadrature remainder is below ten to the minus twelve).
- **Lets through** exact combinatorial integers and small rational group-theory weights (such as hypercharge normalizations one-sixth, one-third, two-thirds, or root-system ranks one through twenty-four) in pure mathematical scripts.
- **Lets through** dimensionless benchmark fixtures inside sealed calibration packages explicitly authorized by `main` when every imported empirical scale is listed and counted in the script's declared input list.

## Specification Six — Zero-Trust Lock and Verification Producer-Import and Passive-Echo Ban

### What the Check Inspects and Refuses
To ensure that lock tests under `"tests/"` and frontier verification test files test mathematical rules and invariants rather than echoing or re-running the producer's own code:
- **Refuses** any lock test for a mathematical or physical claim arc that imports or executes the arc's own producer script — whether by standard `import` statements, dynamic module loading via `importlib` (`import_module` or `spec_from_file_location`), builtin `__import__`, `runpy`, `exec` on file text, or `subprocess` invocation of the producer Python file — and asserts on the dictionary or standard output returned by that producer.
- **Refuses** passive JSON-echo locks that neither execute nor recompute anything, instead opening the producer's committed `.json` or `_out.txt` file and asserting only that hard-coded literal numbers or `"PASS"` strings sit at fixed keys (a lock that pins a value where it should test a rule, `"docs/seats/README.md"` section thirteen item four), **unless** the same test module also contains an independent mathematical recomputation of those quantities from their defining objects without calling the producer.
- **Refuses** silent `pytest.skip` fallbacks inside claim locks when a required commit object, module, or file is absent on a checkout (every claim lock must fail closed rather than skip green).

### What the Check Must Let Through
- **Lets through** independent zero-trust lock tests that construct the matrices, lattices, polynomials, or cohomology cochains directly inside the test file (or via general standard-library arithmetic), recompute the invariant from scratch, and optionally **also** verify that the arc's committed `.json` summary matches that independently recomputed value.
- **Lets through** repository-infrastructure and generator-freshness tests explicitly scoped to testing an **instrument** (`"instrument": true` in `arc_verdict.json`, such as testing `"scripts/gates/gates.py"`, `"scripts/checks/commit_day.py"`, or deterministic page builders like `"build_map.py"` and `"build_where_we_stand.py"`), provided instrument tests include at least one planted-fault case proving the instrument can fail.

## Specification Eight — Pure Commit-Graph Gate Determinism (Clock, Timezone, Environment, Merge Graph, and Clean-Disk Invariance)

### What the Check Inspects and Refuses
Distilled from Review Seventy-Nine's audit of `"scripts/checks/"`, `"scripts/seats/listen.py"`, and `"scripts/gates/gates.py"`, this meta-check audits every gate and check script invoked by `"scripts/gates/gates.py"`:

- **Refuses** any wall-clock or host-timezone call reachable during a gate run — including `time.time`, `datetime.date.today`, `datetime.datetime.now`, and **local-timezone `datetime.date.fromtimestamp`** (which shifts calendar dates across host `TZ` settings on the identical commit) — and requires commit-date monotonicity guards (`commit_day_problems`) to enforce **both** UTC timestamp monotonicity (`%ct`) **and** commit-date monotonicity (`%cs`, the calendar string `"commit_day.py"` actually consumes) across **all reachable commits** (never `--first-parent` alone).
- **Refuses** `--first-parent` restriction on any history guard (`commit_day_problems`, `seal_immutable_problems`, `hash_lists_immutable_problems`, `hash_lists_by_content_problems`), so a side branch that adds and edits or deletes a sealed file or hash list before merging into `main` cannot bypass the guard.

### What the Check Must Let Through
- **Lets through** pure functions of the git object database (`git ls-tree`, `git cat-file`, `git log` over the full reachable directed acyclic graph from `HEAD` with explicit byte decoding or replacement error handling) whose output is bit-for-bit identical across clean clones, dirty working trees with untracked scratch files, arbitrary host `TZ` timezones, arbitrary user environment variables, and arbitrary wall-clock years.
