## 2. G1 — the append-only gate (B1863)

**What is right.** `append_only_problems` is a pure function of the commit graph. It reads every first-parent commit
after the rule's first commit that touches the log and requires the parent's log to be a prefix, or a roll-up with
its archive in that same commit. It returns a failure when there is no repository, when the rule's first commit is
not in the clone, and when HEAD does not descend from it. Your nine tests plant PV1 and PV2 in small repositories,
and the registered control is the gate function failing on a committed deletion.

**Planted here, beyond your tests:**

| # | Planted | Result |
|---|---|---|
| a4 | the deletion made on a side branch and merged | **caught** — a merge is compared with its first parent |
| a1 | one line rewritten inside an archive of the log, `docs/progress/PROGRESS_2026-Q2.md` | **not caught** |
| a2 | 200 lines deleted, then that commit added to the gate's own waiver list in the next commit | **not caught**, and the gate prints "8 commit(s) since f31729801, each an append" |

**Three residuals, in order of weight:**

1. **The archives are not append-only (a1).** A roll-up moves old entries into `docs/progress/`. From then on that
   text is history, and nothing guards it. The gate protects the live file and not what was rolled out of it.
2. **A waiver makes the violation disappear from the output (a2).** After a waiver the gate's sentence says every
   commit was an append, which is then false. The waiver list is in the gate's own source, so the same author can
   write the violation and the waiver. You name the second half yourself (a gate's source can be edited). The first
   half is cheap to mend: print every waiver with its reason on each run, and count the waived commits apart from
   the appends.
3. **History before the rule's first commit is not read.** Stated on the arc. Two rewrites of 2026-07-12 and
   2026-07-13 lie in that part (the audit's reader found them).

**Not a defect of the gate, and worth a line on the record:** a gate that reads history cannot see history that was
rewritten. What protects against that is outside the repository: the remote refusing a forced push to main.

## 3. G2, G3, G4 — sealed files (B1864)

**What is right.** `seal-immutable` reads history as the append-only gate does and refuses an edit, a deletion or a
move of a sealed-style file after the rule's first commit; a new file beside a seal is how an amendment is made.
`seal-ledger-current` recomputes every generated row and refuses a listed file that is gone. The generator no longer
reads the ledger. `seal-order-unshown` reads every seal name, and thirty more arcs are on its list by name, B1297

**What these show:**

1. **The seal protects the rule's text and not the instrument (s1). This is the largest gap left.** A seal in this
   record names two things: what will count, and the code that will compute it. 189 folders carry an
   `ARTIFACT_HASHES.txt` listing the hashed scripts, and no gate reads those files. So the criterion cannot be
   changed after the fact, and the script that evaluates it can. For a comparison with data that is the same
   opening by another door.
2. **A rule under a name outside the four patterns is unprotected (s2),** and the candidate has one.
3. **The patterns reach one folder deep (s3).** 28 sealed-style files lie deeper, most of them old.
4. **Rule-after-record is still invisible (s4).** The order gate asks whether the rule and the record first appear in
   one commit. A rule that first appears *later* than its record is the worse case and passes. The audit's reader
   found no such arc on main, so this is a hole and not a defect in the record.
5. **Waivers: as for G1.**

**Proposed, in the order the seat would do them:** a gate that recomputes every `ARTIFACT_HASHES.txt`, with the same
immutability rule for the files it lists; the order gate requiring the seal's first commit to be a strict ancestor
of the record's; the patterns at any depth under the arc; and the waivers printed.
