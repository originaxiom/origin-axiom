# ADDENDUM 2026-09-02 (B1240) -- the reproduction closure is vendored; the lock now runs

**What was wrong.** `verification/reproduce_all.sh` was pinned by `tests/` only as the STRING `REPRODUCES` found in
a committed record; the runner itself could not run on a fresh clone. Its certificates lived on
`origin/outside-bench` and were to be fetched by name, but the fetch list omitted the sibling files the certificates
load at runtime, and the cited run record `reproduce.log` is gitignored. This is the E57 shape
(a lock without its tool) -- B1240 finds it in five harvest arcs; this is one of them.

**What changed.** The full transitive closure at `dc937010` (26 files: code, data, expected outputs) is now under
`verification/certificates/` and `verification/outputs/` with `VENDORED_FROM.txt` (sha256 per file).
The runner takes `CERTS=<name>` to run one certificate and `cd`s to its own directory. On the main bench
(2026-09-02) it prints REPRODUCES for 11/11 certificates (B1240
`verification/closure_run.txt`). `tests/test_reproduce_runners_live.py` executes it -- the fastest
certificate (`cusp_beat`) in the default lane, all of them under `OA_SLOW=1`.

**What did not change.** No verdict, no number: the certificates are the cloud seat's, byte-identical to
the pinned SHA; the vendoring makes the existing claim checkable, it does not extend it.
The `c2b_ohtsuki_bridge` expected output was never committed at source; the file under `outputs/` is our own deterministic run, labelled GENERATED in VENDORED_FROM.txt -- it pins reproducibility of the run, not an independent expectation.
